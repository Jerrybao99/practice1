# 数据传输

## 未来意图

1. **项目交付全流程的结构化交接**：将量潮数据项目从需求调研到最终验收的五个阶段（调研、谈判、实施、验收、复盘）中每一份文档、每一次状态变更、每一笔交付物都纳入统一的结构化体系。每个阶段结束时形成可追溯的"权责流转标志"——前一阶段明确交付标准，后一阶段据此验收，消除口头约定导致的扯皮空间。

> 日志（2026-07-27）完整定义了五阶段项目流程及对应文档，PRD 的用户故事地图明确标注了每个节点的"权责流转标志"和"协同产出"。qtdata CLI 的 Blueprint/Scope/Quotation/Delivery 四个命令恰对应这些阶段关键文档的结构化转换，说明这套流转逻辑已经落实到命令行工具层面。

2. **交付资产的标准化生命周期管理**：将每次客户交付的数据集、处理代码、质量报告、验收记录统一建模为"交付资产（Asset）"，支持从草稿→提交→待验收→已通过/需修改→归档的完整状态机，每个版本的资产均可独立追溯和重新交付。资产不仅包含最终文件，还包含其数据血缘、处理流程和验收凭证。

> 日志提出"从档案到案例形成一个交付结果"（2026-07-10），Provider ROADMAP 明确 Asset 模型包含"交付物类型、版本、状态、关联流程"，Studio ROADMAP 规划了 `qtdata-asset` package 用于"交付物模型、版本管理、状态追踪"。storage.py 中的 Task 类型已按业务语义分为 requirement/agreement/execution/acceptance 四类，说明资产分类已进入代码建模阶段。

3. **客户透明交付体验**：构建面向非技术岗位的可视化交付界面，让商务经理和客户无需理解技术细节即可掌握项目全貌——从项目看板（名称、状态、进度百分比）到交付时间线（每个阶段做了什么、结果如何）再到数据质量报告（契约指标达成率以进度条/仪表盘形式呈现）。透明化不是信息过载，而是将技术复杂性转化为业务可理解的交付语言。

> 日志（2026-07-27）详细描述了 5 个用户旅程中的痛点与产品功能，反复强调"非技术可读模式""以进度条或仪表盘形式展示"。Studio 的 dashboard_screen.dart 和 project_detail_screen.dart 已实现项目卡片、过滤筛选、交付进度条、交付目标树、数据蓝图流程步骤和交付时间线，说明可视化交付体验并非远期规划而是当前正在迭代的版本。

## 拟定工作范围

- **CLI 端**：完成 Blueprint/Scope/Quotation/Delivery 四个命令的 LLM 集成，实现从自然语言文档到结构化配置文件的自动转换。现阶段输入为 Markdown（日志、需求记录），输出为 CUE（Blueprint）和 JSON（Scope/Quotation/Delivery）。后续接入真实客户对话场景。
- **Provider 端**：在已有 Project/Task CRUD 基础上，实现 Process（数据处理流程）和 Asset（交付资产）两个核心资源的路由与持久化，承载 Studio 端的数据页面和资产页面。
- **Studio 端**：在已有的仪表盘和项目详情页基础上，新增数据页面（展示数据处理流程的步骤、状态、中间产物）和资产页面（展示交付物列表、版本历史、下载链接、质量报告），完成三端（CLI + Provider + Studio）的业务闭环。

## 未来实现

- **平台**：qtdata 三端架构（Rust CLI + Python FastAPI Provider + Flutter Studio）已在仓库中搭建完成并通过 E2E 测试验证（tests/ 目录包含 Playwright 系的截图和录屏工具）。继续在此架构上增量迭代。
- **工具**：CLI 层复用 `quanttide_agent` 库的 LLM 封装，调用 DeepSeek API 将 Markdown 解析为结构化输出。Provider 层复用 `fastapi_quanttide_project` 的 Router 工厂模式快速生成 CRUD 端点。Studio 层按 ROADMAP 规划拆分为 `qtdata-data` 和 `qtdata-asset` 两个 package，保持组件内聚。
- **数据存储**：Provider 从当前内存 dict 切换为持久化数据库（SQLite 或 PostgreSQL），支持多工作空间隔离。CLI 输出沿用 `data/qtdata/<workspace>/` 目录结构，与 journal 的默认 workspace 对齐。

## 设计原则

1. **先文档后数据**：每个业务动作的第一步是将非结构化信息（客户口述、会议记录、飞书文档）转为结构化文档（Blueprint/Scope/Quotation），用文档固化共识，数据操作才可校验、可对账。

2. **非技术人员优先**：界面和交互设计以商务经理和客户为第一用户，技术细节按需展开而非默认呈现。交付进度用百分比和进度条，质量用红绿灯状态，避免原始数值堆砌。

3. **流转即验收**：每次交接（需求→规格、规格→合同、处理→交付物、交付→验收）必须产生可追溯的"权责流转标志"——一份双方确认的结构化记录，作为下一阶段的输入和争议解决的依据。
