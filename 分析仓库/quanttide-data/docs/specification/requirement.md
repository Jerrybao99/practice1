# Requirement — 数据需求文档（DRD）

> 层次：Requirement | 动词：clarify | 受众：客户/业务方 | 格式：Markdown

---

## 1. 定义

数据需求文档（Data Requirements Document，DRD）是数据工程流程的入口工件。它描述**客户想要什么**，使用业务语言而非技术术语。DRD 由 `clarify` 动作从客户聊天记录或上下文中提取并结构化。

DRD MUST 回答以下三个问题：

1. **为什么做**：业务背景和目标
2. **有什么输入**：客户提供的数据来源、格式和范围
3. **要什么输出**：期望的交付物形式和质量标准

---

## 2. 格式与位置

### 2.1 格式

DRD MUST 使用 Markdown 格式。DRD 的受众是客户和业务方，MUST NOT 包含 YAML 结构或技术实现细节。

### 2.2 文件位置

DRD 文件 MUST 存放在 `.quanttide/data/requirement/` 目录下。

文件命名 SHOULD 使用项目标识符，如 `<project-name>.md`。

---

## 3. 结构定义

一份符合规范的 DRD MUST 包含以下章节：

### 3.1 业务目标

| 字段 | 约束 |
|------|------|
| `业务目标` | MUST 存在。一段或多段自然语言描述，说明项目要解决的业务问题和预期价值。 |

### 3.2 数据范围

| 字段 | 约束 |
|------|------|
| `数据范围` | MUST 存在。描述数据来源、类型和预估规模。SHOULD 包含数据敏感度说明（是否需要脱敏）。 |

### 3.3 输入要求

| 字段 | 约束 |
|------|------|
| `输入要求` | MAY 存在。描述客户需要提供的数据：文件格式、字段说明、交付方式和频次。如果客户无需提供数据（数据由我方采集），MAY 省略。 |

### 3.4 输出期望

| 字段 | 约束 |
|------|------|
| `输出期望` | MUST 存在。描述期望的交付物：格式（CSV/JSON/Parquet）、结构（面板数据/长表/文档分类结果）、关键指标定义。 |

### 3.5 约束与假设

| 字段 | 约束 |
|------|------|
| `约束与假设` | SHOULD 存在。列出已知的约束条件：时间、预算、数据质量假设、合规要求。如果无特殊约束，MAY 省略。 |

### 3.6 验收标准

| 字段 | 约束 |
|------|------|
| `验收标准` | MUST 存在。可验证的完成判据列表。每条标准 MUST 可被"通过/不通过"判定。 |

---

## 4. 模板

```markdown
# <项目名称> — 数据需求文档

## 业务目标

<项目要解决的业务问题，用自然语言描述>

## 数据范围

<数据来源、类型、规模、敏感度>

## 输入要求

<客户需要提供的文件、格式、频次。如无则省略>

## 输出期望

<期望的交付物：格式、结构、关键指标>

## 约束与假设

<时间/预算/质量假设/合规要求。如无则省略>

## 验收标准

- [ ] <可验证的判据 1>
- [ ] <可验证的判据 2>
```

---

## 5. 示例

```markdown
# GHTorrent 用户活动数据提取 — 数据需求文档

## 业务目标

从 GHTorrent 开源数据库的 MySQL dump 中，为一批指定的 GitHub 用户提取每日活动面板数据，用于开源社区行为研究。

## 数据范围

- 来源：GHTorrent MySQL dump（公开数据）
- 规模：数百 GB 原始数据，数万目标用户
- 敏感度：输出需对用户标识做脱敏处理

## 输出期望

- 格式：CSV
- 结构：面板数据，每行 = 一个用户一天的全部活动聚合
- 关键指标：push 次数、PR 次数、Issue 评论次数等多项活动指标
- 控制变量：bot 识别标记

## 约束与假设

- 时间：两周内完成
- 质量：bot 识别准确率优先于覆盖率
- 数据需去重

## 验收标准

- [ ] CSV 每日一行，列数固定
- [ ] 用户标识已脱敏
- [ ] Bot 识别结果可复现
- [ ] 去重验证通过（无重复行）
```
